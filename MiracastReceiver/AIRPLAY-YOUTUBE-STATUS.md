# AirPlay 投屏 YouTube：测试进展与待解决问题

更新日期：2026-11-07。关联反馈：[Issue #34](https://github.com/weekdayjast/MiracastReceiver/issues/34)。

## 适用范围

本文记录 iPhone YouTube App 通过 AirPlay 向 Android TV 投屏的调试结果，区分已经验证的修复、已实现但仍需回归的功能，以及尚未解决的问题。

- 基线：v1.2.13（`cfbd055`）接入 UxPlay 协议层。
- 已验证设备：Sony BRAVIA_VH22，ARM32，测试电视 `192.168.2.116`。
- 测试工程：仓库根目录下 `_release/uxplay-v1.2.13-baseline/MiracastReceiver`。
- 最近安装包：`_release/miracast-v1.2.13-uxplay-configured-name-arm32.apk`，版本名 `1.2.13-uxplay-base`。

这些结果针对上述测试工程和测试包，不代表全部修复已合入主工程或正式发布版，也不代表其他电视均已通过验证。`_release` 下的工程、安装包和日志是本地调试产物，未随本文纳入版本控制。

## 当前架构

UxPlay 负责 AirPlay 发现、连接、请求处理及 HLS 会话管理；视频渲染由 Android 播放器完成，UxPlay 本身不替代播放器。

- YouTube HLS 视频：交给 Media3 播放，支持自适应清晰度和字幕轨道。
- 其他视频 URL：保留 v1.2.13 的 Android MediaPlayer 路径，遇到部分不支持或格式错误时回退至 Media3。
- 屏幕镜像：通过接入的镜像渲染管线解码与显示，与 HLS 视频播放分别处理。

因此，目前仍保留 Media3，不能把这套方案理解为“移除 Media3、只使用 UxPlay”。

## 已解决或已通过对应场景验证

| 问题 | 当前处理 | 验证与边界 |
| --- | --- | --- |
| YouTube 投屏黑屏、只有进度条或提示“出错了／视频无法播放” | 在 v1.2.13 基线上接入 UxPlay，HLS 交给兼容的播放器处理 | 用户确认正常播放；广告衔接问题仍单独列为待解决 |
| 播放成功后切换其他视频报错 | 使用 UxPlay 管理播放会话与后续播放请求 | 用户确认正常播放、换片也可播放；仍需扩展连续换片回归 |
| 广告切换期间部分属性请求导致进程崩溃、AirPlay 断开 | 原生补丁 0011 允许在当前视频已被移除时处理属性请求，避免断言退出 | 修复已定位的请求顺序崩溃，不等于所有广告切换均已修复 |
| 视频或广告自然结束时接收端主动结束会话 | 本地播放器结束后保留最终进度、总时长、暂停状态及就绪状态，不立即停止视频或发布 `duration=-1` | 已移除这一主动断开路径；广告结束仍存在不自动进入正片的问题 |
| 屏幕镜像内容被放大、裁切 | 每次渲染读取当前 EGL 窗口尺寸，避免 Surface 调整后继续使用旧视口 | 已针对镜像 Surface 尺寸变化修正；其他机型及旋转组合仍需回归 |
| 清晰度变化时卡顿并出现 VP9 解码错误 | 对 BRAVIA_VH22 的 `OMX.MTK.VIDEO.DECODER.VP9` 禁用跨分辨率的解码器复用，变化时重建解码器 | 日志已验证 720p、1080p 切换及解码器重建；属于该机型的兼容处理 |
| 有声音没有画面 | 为 PlayerActivity 发布的 Surface 增加实例归属，防止旧页面销毁时清掉新页面的 Surface；HLS 定期检查有效输出目标 | 用户确认画面恢复，日志有首帧输出 |
| 画质被固定上限或强制最高码率影响 | HLS 清除固定视频尺寸和视口上限，并关闭强制最高码率，恢复自适应选轨 | 实际解码日志出现过 1440p、2160p；不保证任何片源、网络下都持续最高画质 |
| AirPlay 名称与设置不一致 | 去掉测试名称后缀，使用设置中的设备名称；设置变更刷新 AirPlay 和 RAOP 的发现广播 | 已确认使用“客厅电视”；运行时原生内部元数据名称仍保留启动值，详见待回归项 |

## 已实现，仍需完整回归

### 手机字幕选择同步

已实现以下链路：

1. 从手机发来的 `selectedMediaArray` 中解析字幕语言、名称及开关。
2. 经原生补丁 0012 和 JNI 回调转交 Android 播放器。
3. Media3 选择对应字幕轨道，通过独立字幕视图叠加显示；关闭字幕时清空内容。

字幕默认关闭，由手机选择决定，不强制使用电视端默认语言，也不随意替换成其他语言。音轨选择不会覆盖字幕选择。

已完成字幕选择策略的 6 项单元测试，以及中文、英文、仅音轨更新、关闭字幕的 4 项协议回调验证；真实投屏日志也收到过字幕语言选择。仍需逐项确认实际字幕可见、时序正确，并覆盖换片、广告、拖动进度后的字幕状态。没有可用字幕轨道时不能凭空显示字幕。

### 拖动进度

此前一次“拖动后卡死”对应跳到约 36:40，而视频总长约 36:51。日志显示约 3 秒缓冲后恢复播放，随后正常结束；用户确认拖到结尾附近，之后也确认可以正常播放。

这一次未确认是持续卡死，但还需回归中段跳转、连续快进／后退及高分辨率下的拖动。

## 待解决问题

### 1. 广告播完后不能可靠地自动进入正片

**现象：** 不点“跳过广告”，等待广告自然结束，可能停住、不进入正片，部分历史测试还出现过错误或断开。

已经修复接收端在自然结束时立即停止会话的行为，但自动衔接仍未验证成功。

一次关键日志记录：

- 21:35:49：广告播放结束，接收端保留最终状态。
- 随后手机轮询时，接收端返回最终进度和总时长、播放速率 0、就绪状态。
- 21:35:54：收到手机的停止请求。
- 21:36:09：开始播放长视频。

用户确认期间手动点过跳过、重试或重新投屏，因此后续长视频播放不能作为“广告自动进入正片”的成功证据。

**下一步：** 在完全不操作手机的情况下抓取广告结束前后的完整协议，核对播放结束事件、状态查询、播放列表移除与下一条播放请求。需要确认双方缺少哪一步交互，不能只凭结束时间推定原因。

### 2. 手机手动选画质与电视实际分辨率尚未同步

**现象：** YouTube 菜单显示“AirPlay 不支持高级选项”；部分情况下仍能看到具体分辨率列表，但选择后电视不一定按该值播放。手机显示 1080p 时，电视实际解码日志曾是 2560×1440。

当前电视播放器根据可用 HLS 轨道、带宽和解码能力自适应选择画质。此前按“480p → 1080p → 自动”操作抓取的日志中，没有识别到明确的画质控制请求，尚未实现手机手动画质指令到电视播放器的映射。

因此：

- 手机菜单显示的数值不能直接当作电视实际解码分辨率，应以播放器输入格式和输出尺寸日志为准。
- 播放列表包含某个分辨率，不代表播放器正在播放它。
- 当前没有强制最高码率，也没有固定限制为 1080p；能否播放某档画质取决于实际片源、网络和解码器。

**连接时的能力声明：** 当前 UxPlay 的 `/server-info` 声明视频、HLS 等能力和设备信息，没有发送一份 480p／1080p／2160p 分辨率列表；镜像连接中的宽高也不能直接当作 HLS 画质上限。HLS 片源通过多版本播放列表提供各档画质。

YouTube 如何决定禁用高级画质菜单，其内部判断规则尚未确认。不能据此认定接收端少报了分辨率，也不能承诺修改某个能力位就能解锁菜单。

**下一步：** 对照其他接收端在同一手机、同一视频下的能力响应和画质操作日志，确认手机是否发送控制请求、是否更新播放列表，以及实际选轨是否变化。

## 合入与兼容性待办

- 将测试工程的有效修复整理回主工程，避免与此前 Kotlin 协议／转发实验混淆；合入前核对差异并回归。
- 补测其他电视、ARM64、不同 iOS／YouTube 版本，不能把单台 ARM32 电视的结果推广到全部设备。
- 回归两种连接顺序：先开屏幕镜像再播放 YouTube；先播放 YouTube 再选择 AirPlay。覆盖广告、换片以及镜像与视频模式切换。
- 回归连续换片、长时间播放、网络波动、手机断开重连和接收服务重启。
- 验证运行中改名后的重新发现；当前发现广播会更新，原生内部元数据名称在下次启动时重新初始化。
- 检查 UxPlay 及其依赖的许可证、源码与补丁提供方式。测试工程已保留来源说明；正式集成发布前仍需核对 GPLv3 等要求，不能仅沿用主仓库 MIT 标记。

## 推荐回归记录

| 场景 | 通过条件 |
| --- | --- |
| 直接播放、连续换片 | 画面声音正常，无“出错了”，无需重新连接 |
| 广告自然结束 | 全程不手动操作，自动进入正片，会话保持有效 |
| 跳过广告 | 正片开始播放，无崩溃、持续黑屏或断开 |
| 镜像期间播放 YouTube | 画面比例正常，进入广告及切回视频不出错 |
| 清晰度变化 | 记录实际输入／输出尺寸，能恢复播放，无硬件解码错误 |
| 字幕开关与语言切换 | 电视跟随手机选择显示，关闭后立即消失，换片状态正确 |
| 拖动进度 | 中段、结尾附近和连续拖动后均能恢复或正常结束 |
| 改名与重连 | 发现列表使用设置名称，重新连接后播放正常 |

每次记录手机操作时间、视频时长、是否手动跳过／重试、实际播放分辨率和错误日志，避免把手动恢复误判为自动恢复。
